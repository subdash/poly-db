# rust-kvs on Kubernetes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the single-node kvs-server on a local Kubernetes cluster, and use
that cluster to demonstrate the durability properties the store already claims.

**Architecture:** A two-stage container image built natively for `linux/arm64`,
deployed as a single-replica StatefulSet with a per-pod PersistentVolumeClaim, a
headless Service for pod identity and a ClusterIP Service for client traffic, and
three probes whose interaction is the point of the exercise. The application
gains environment-variable configuration and a `/ready` endpoint; nothing about
its storage or concurrency model changes.

**Tech Stack:** Docker, kind (Kubernetes in Docker), kubectl, Debian bookworm
base images, clap's `env` feature.

**Spec:** `docs/superpowers/specs/2026-09-10-rust-kvs-k8s-design.md`

## Global Constraints

- **You write the manifests and the Dockerfile.** This plan gives every exact
  value — field names, paths, thresholds, image tags, env var names — and what
  each one does, but the YAML and the Dockerfile are yours to author. That is the
  thing being learned here.
- **Rust follows the MVP convention:** complete failing tests are given; no
  implementation bodies.
- **Cluster:** kind on Docker Desktop, macOS, Apple Silicon. Images build
  natively for `linux/arm64`; no cross-compilation.
- **Namespace:** `kvs`. Every `kubectl` command in this plan assumes
  `-n kvs` unless stated otherwise.
- **Image tag:** `kvs-server:dev`. Never `latest` — see Task 2, Step 7.
- **Names:** StatefulSet `kvs`, headless Service `kvs-headless`, ClusterIP
  Service `kvs`, PVC template `data`, container port name `http`.
- **Environment variables:** `KVS_ADDR`, `KVS_DATA_DIR`, `KVS_FSYNC`.
- **Container paths:** binary at `/usr/local/bin/kvs-server`, data at
  `/var/lib/kvs`.
- **Every Rust task ends green:** `cargo fmt`, `cargo clippy --all-targets --
  -D warnings`, `cargo test --workspace`. The suite is at 66 tests before this
  plan starts.

## File Structure

```
Dockerfile                      two-stage build; rust:1-bookworm -> debian:bookworm-slim
.dockerignore                   excludes target/ from the build context
deploy/k8s/namespace.yaml       the kvs namespace
deploy/k8s/service.yaml         both Services: kvs-headless and kvs
deploy/k8s/statefulset.yaml     the StatefulSet, including probes and resources
deploy/README.md                the verification checklist from Task 6
crates/kvs-server/src/config.rs env attributes + a test module      (modified)
crates/kvs-server/src/routes.rs the /ready route and handler        (modified)
crates/kvs-server/tests/api.rs  tests for /ready                    (modified)
Cargo.toml                      clap gains the "env" feature        (modified)
```

Manifests are split by lifetime rather than by kind: the namespace is created
once and never touched, the Services rarely change, and the StatefulSet changes
on every image rebuild. Putting both Services in one file is deliberate — they
are two halves of one addressing story and are easier to understand side by side.

## Task 1: Environment configuration and the `/ready` endpoint

**Files:**
- Modify: `Cargo.toml` (workspace `clap` dependency)
- Modify: `crates/kvs-server/src/config.rs`
- Modify: `crates/kvs-server/src/routes.rs`
- Test: `crates/kvs-server/tests/api.rs`

**Interfaces:**
- Consumes: `Config`, `FsyncArg`, `routes::router`.
- Produces: `GET /ready` returning `200` with `{"status":"ready"}`; `Config`
  fields readable from `KVS_ADDR`, `KVS_DATA_DIR`, `KVS_FSYNC`.

**Why this task exists:** two independent problems, both blocking the container.
Kubernetes supplies configuration through the environment, not argv. And liveness
and readiness are different questions with opposite consequences — a liveness
failure restarts the pod, a readiness failure only withholds traffic — so they
need different endpoints even while both answers happen to be the same.

**Design note:** the defaults do not change. `--addr` stays `127.0.0.1:3000`,
because binding a development server to every interface by default is unfriendly.
The container sets `0.0.0.0:3000` explicitly through the environment. Flags
continue to take precedence over environment variables, which is clap's ordering
and the one you want: an operator debugging a pod can override the deployment's
configuration from the command line.

- [ ] **Step 1: Write the failing tests**

```rust
// append to crates/kvs-server/tests/api.rs

#[tokio::test]
async fn ready_reports_ready() {
    let app = test_app();
    let (status, body) = send(&app, get("/ready")).await;

    assert_eq!(status, StatusCode::OK);
    let json: serde_json::Value = serde_json::from_slice(&body).expect("json body");
    assert_eq!(json["status"], "ready");
}

#[tokio::test]
async fn health_and_ready_are_separate_routes() {
    let app = test_app();

    let (health_status, health_body) = send(&app, get("/health")).await;
    let (ready_status, ready_body) = send(&app, get("/ready")).await;

    assert_eq!(health_status, StatusCode::OK);
    assert_eq!(ready_status, StatusCode::OK);

    let health: serde_json::Value = serde_json::from_slice(&health_body).expect("json");
    let ready: serde_json::Value = serde_json::from_slice(&ready_body).expect("json");

    assert_eq!(health["status"], "ok");
    assert_eq!(ready["status"], "ready");
}
```

```rust
// append to crates/kvs-server/src/config.rs

#[cfg(test)]
mod tests {
    use super::*;
    use clap::Parser;

    #[test]
    fn flags_set_every_field() {
        let config = Config::parse_from([
            "kvs-server",
            "--addr",
            "0.0.0.0:9999",
            "--data-dir",
            "/var/lib/kvs",
            "--fsync",
            "never",
        ]);

        assert_eq!(config.addr.to_string(), "0.0.0.0:9999");
        assert_eq!(config.data_dir, PathBuf::from("/var/lib/kvs"));
        assert!(matches!(config.fsync, FsyncArg::Never));
    }

    #[test]
    fn the_defaults_are_loopback_and_a_relative_data_dir() {
        let config = Config::parse_from(["kvs-server"]);

        assert_eq!(
            config.addr.to_string(),
            "127.0.0.1:3000",
            "the default must stay loopback; the container overrides it"
        );
        assert_eq!(config.data_dir, PathBuf::from("./data"));
        assert!(matches!(config.fsync, FsyncArg::Always));
    }
}
```

**A caveat about the second test.** `parse_from` still reads the process
environment, so this test fails if `KVS_ADDR`, `KVS_DATA_DIR`, or `KVS_FSYNC` is
set in the shell that runs `cargo test`. That is inherent — clap reads
`std::env`, which is process-global, and Rust runs tests in parallel threads
within one process, so there is no sound way to set an environment variable for
one test without racing every other. Verify the environment path manually in
Step 6 instead of trying to test it.

- [ ] **Step 4: Add the env attributes and the route**

In `config.rs`, each `#[arg(...)]` attribute gains an `env` key. The three

In `routes.rs`, add a `/ready` route to the router and a handler beside `health`.

- Return `Json`, not `&'static str`. A string literal is served as
  `text/plain` even when its content is JSON.

## Task 2: The container image

**Files:**
- Create: `Dockerfile`
- Create: `.dockerignore`

**Interfaces:**
- Consumes: the `kvs-server` binary produced by `cargo build --release`.
- Produces: image `kvs-server:dev`, running as a non-root user, serving on
  container port 3000, storing data at `/var/lib/kvs`.

**Why this task exists:** the image is the unit Kubernetes schedules. Everything
after this is orchestration; this is the only task that decides what actually
runs.

**Design note — why `debian:bookworm-slim` and not distroless.** Distroless is
smaller and carries less attack surface, but it has no shell, so
`kubectl exec -it -- sh` does not work. While learning, a shell inside a running
pod is one of the more useful things available. The spec records distroless as a
hardening step for later.

- [ ] **Step 1: Write `.dockerignore` first**

It must exclude `target/` before you run any build. Without it, Docker uploads
the entire build directory as the build context — gigabytes, on every
invocation, before the Dockerfile's first instruction runs.

Contents: `target`, `.git`, `data`, and `docs`.

- [ ] **Step 2: Write the Dockerfile**

Two stages.

**Builder** — `FROM rust:1-bookworm AS builder`. Copy the workspace in, run
`cargo build --release -p kvs-server`. The binary lands at
`target/release/kvs-server`.

**Runtime** — `FROM debian:bookworm-slim`. Create an unprivileged user and
group, create `/var/lib/kvs` owned by that user, copy the binary from the builder
stage to `/usr/local/bin/kvs-server`, `EXPOSE 3000`, set `USER` to the
unprivileged user, and set the entrypoint to the binary.

**Use uid and gid `10001`, with the user and group both named `kvs`.** The exact
number does not matter to Linux, but it must be *known*, because Task 4's pod
spec has to repeat it in two places: `runAsUser` and `fsGroup`. Pick it here,
write it down, and use the same number there. A high, fixed id also avoids
colliding with distribution-assigned system accounts.

Three things that will bite otherwise:

- **The Debian versions must match.** `rust:1-bookworm` produces a binary linked
  against bookworm's glibc. Running it on `debian:bullseye-slim` fails with
  `no such file or directory` naming a file that visibly exists — the message
  refers to the missing dynamic loader, not to the binary.
- **Do not set `CMD` arguments for the address or data directory.** Those come
  from the environment in Task 4. An `ENTRYPOINT` with no `CMD` is what you want,
  so the pod spec's `env` is the only source of configuration.
- **Copy from the builder by stage name**, not by rebuilding. `COPY --from=builder`
  is the whole point of the two-stage split; without it the final image carries
  the entire Rust toolchain.

- [ ] **Step 3: Build the image**

```bash
docker build -t kvs-server:dev .
```

Expected: a successful build. Check the size:

```bash
docker images kvs-server:dev
```

Expected: roughly 80–120 MB. If it is over a gigabyte, the `COPY --from=builder`
is missing and you have shipped the builder stage.

This build takes several minutes the first time. Subsequent builds recompile
every dependency whenever any source file changes, because the whole workspace
is one layer. If that becomes tedious, the standard remedy is to copy the
manifests first, build a stub `main.rs`, then copy the real sources — so the
dependency layer is invalidated only by manifest changes. It is fiddlier in a
workspace than in a single crate; `cargo-chef` automates it correctly. Neither is
required to finish this plan.

- [ ] **Step 4: Run the container and verify it serves**

```bash
docker run --rm -d --name kvs-test \
  -p 3000:3000 \
  -e KVS_ADDR=0.0.0.0:3000 \
  -e KVS_DATA_DIR=/var/lib/kvs \
  kvs-server:dev
```

Then, from the host:

```bash
curl -i -X PUT localhost:3000/v1/kv/greeting \
  -H 'content-type: application/json' -d '{"value":"hello"}'
curl -i localhost:3000/v1/kv/greeting
curl -i localhost:3000/health
curl -i localhost:3000/ready
```

Expected: 204, then 200 with the value, then two 200s.

- [ ] **Step 5: Prove the bind address matters**

Stop the container, then start it again **without** `KVS_ADDR`:

```bash
docker stop kvs-test
docker run --rm -d --name kvs-test -p 3000:3000 kvs-server:dev
curl -i localhost:3000/health
```

Expected: connection refused. The server bound `127.0.0.1` inside the container's
own network namespace, which nothing outside that container can reach — not the
host, and in Kubernetes, not the kubelet's probes either.

This is worth doing deliberately once. It is among the most common first-day
container failures, and the symptom — a process that is plainly running and
plainly listening, refusing every connection — gives no hint about the cause.

```bash
docker stop kvs-test
```

- [ ] **Step 6: Confirm the container runs as non-root**

```bash
docker run --rm kvs-server:dev id
```

This fails, because the entrypoint is the server binary — which is correct.
Override it:

```bash
docker run --rm --entrypoint id kvs-server:dev
```

Expected: a non-zero `uid`. If it reports `uid=0(root)`, the `USER` instruction
is missing or is placed before the `COPY` that needs root.

- [ ] **Step 7: A note on the tag**

The image is tagged `dev`, never `latest`, and this matters in Task 3.

Kubernetes defaults `imagePullPolicy` to `Always` when a tag is `latest` or
absent, and to `IfNotPresent` for any other tag. An image tagged
`kvs-server:latest` and loaded into kind therefore fails with `ErrImagePull` —
the cluster tries to pull from a registry an image it already has locally — while
`kvs-server:dev` works. Task 4 sets the policy explicitly anyway, so the
behaviour does not rest on remembering this convention.

- [ ] **Step 8: Commit**

```bash
git add Dockerfile .dockerignore
git commit -m "build: add a two-stage container image for kvs-server"
```

## Task 4: Namespace, Services, and the StatefulSet

**Files:**
- Create: `deploy/k8s/namespace.yaml`
- Create: `deploy/k8s/service.yaml`
- Create: `deploy/k8s/statefulset.yaml`

**Interfaces:**
- Consumes: image `kvs-server:dev` loaded in Task 3; the `KVS_*` environment
  variables from Task 1.
- Produces: a running pod `kvs-0` in namespace `kvs`, serving on port 3000,
  reachable through `kubectl port-forward`, with its data on a
  PersistentVolumeClaim that outlives the pod.

**Why a StatefulSet and not a Deployment:** three reasons, all pointing at
replication. `volumeClaimTemplates` provisions storage *per pod*, so scaling to
three replicas later creates three independent volumes rather than three engines
appending to one log and corrupting it. Pod identity is stable, so `kvs-0` keeps
its name and its volume across restarts. And updates are ordered, one pod at a
time, which becomes the availability mechanism once there is more than one pod.

A Deployment with a hand-written PVC would additionally need
`strategy: Recreate`, because a `ReadWriteOnce` volume attaches to one node at a
time: the default rolling update deadlocks, with the new pod unable to mount the
volume until the old pod releases it, and the old pod not terminated until the
new one is ready.

- [ ] **Step 1: Write `namespace.yaml`**

A single `Namespace` object named `kvs`. Four lines.

- [ ] **Step 2: Write `service.yaml`**

Two `Service` objects in one file, separated by a `---` document break. Both
select pods by the label you will put on the StatefulSet's pod template — use
`app.kubernetes.io/name: kvs`.

| | `kvs-headless` | `kvs` |
|---|---|---|
| `spec.clusterIP` | `None` | omitted (assigned) |
| Purpose | per-pod DNS identity | client traffic |
| Port | 3000 → `http` | 3000 → `http` |

The **headless** Service is required by the StatefulSet's `serviceName` field. It
gives every pod individually addressable DNS —
`kvs-0.kvs-headless.kvs.svc.cluster.local` — which is what a replica will need to
reach a specific peer. A normal Service load-balances across pods and cannot
address one.

The **ClusterIP** Service is what clients use. It is where readiness gating
becomes observable: a pod failing its readiness probe is removed from this
Service's endpoint list and stops receiving traffic, without being restarted.

Name the port `http` in both. Naming it lets the probes in Task 5 reference
`port: http` rather than repeating `3000`, so the number lives in one place.

- [ ] **Step 3: Write `statefulset.yaml`**

One `StatefulSet` named `kvs`. The fields that matter, with exact values:

**Top level**

| Field | Value | Why |
|---|---|---|
| `spec.serviceName` | `kvs-headless` | must name the headless Service |
| `spec.replicas` | `1` | one writer; see the spec |
| `spec.selector.matchLabels` | `app.kubernetes.io/name: kvs` | must equal the pod template's labels |

**Pod spec**

| Field | Value | Why |
|---|---|---|
| `terminationGracePeriodSeconds` | `30` | the window your shutdown chain runs in |
| `securityContext.runAsNonRoot` | `true` | refuses to start a root container |
| `securityContext.runAsUser` | `10001` | the uid from the Dockerfile |
| `securityContext.fsGroup` | `10001` | makes the volume writable |

**Container**

| Field | Value |
|---|---|
| `image` | `kvs-server:dev` |
| `imagePullPolicy` | `IfNotPresent` |
| `ports[0]` | `containerPort: 3000`, `name: http` |
| `env` | `KVS_ADDR=0.0.0.0:3000`, `KVS_DATA_DIR=/var/lib/kvs`, `KVS_FSYNC=always` |
| `volumeMounts[0]` | `name: data`, `mountPath: /var/lib/kvs` |
| `resources.requests` | `cpu: 100m`, `memory: 64Mi` |
| `resources.limits` | `cpu: 1000m`, `memory: 512Mi` |

**Volume claim template**

| Field | Value |
|---|---|
| `metadata.name` | `data` — must match the `volumeMounts` name |
| `spec.accessModes` | `[ReadWriteOnce]` |
| `spec.resources.requests.storage` | `1Gi` |

Four notes on these values:

**`fsGroup` is the one that will fail confusingly.** A freshly provisioned volume
is owned by root. Your container runs as a non-root user, so without `fsGroup`
the engine cannot create its log file and the pod crash-loops with a permission
error on the very first thing it does. Setting `fsGroup` makes the kubelet change
the volume's group ownership on mount. It must equal the gid you created in the
Dockerfile — `10001`.

**`KVS_ADDR` must be `0.0.0.0`,** for the reason you proved in Task 2, Step 5.
The kubelet's probes arrive on the pod's own IP; a loopback bind refuses them,
and the pod fails its probes forever while appearing to run correctly.

**The memory limit interacts with your channel capacity, and the arithmetic is
worth doing.** `main` spawns the writer with a capacity of 1024, and
`MAX_VALUE_BYTES` is 1 MiB — so a saturated channel can hold on the order of a
gibibyte of queued `Request` values, well past a 512Mi limit. In practice a
client would have to sustain a flood of near-maximum values to get there, and
512Mi is a reasonable starting point. But it is a real property of the current
design, not a hypothetical: the bound on queued write memory is
`capacity × MAX_VALUE_BYTES`, and nothing currently enforces a relationship
between that product and the pod's limit. Task 6's optional fifth experiment
makes the ceiling concrete.

**`resources.requests` is what the scheduler uses; `limits` is what the kernel
enforces.** Requests reserve capacity when placing the pod. Exceeding the CPU
limit throttles; exceeding the memory limit is an OOM kill. On a one-node kind
cluster the scheduling half is uninteresting, but the values must be present for
the enforcement half.

Do **not** add probes yet. Task 5 adds them deliberately, so you can see what
changes.

## Task 5: Probes

**Files:**
- Modify: `deploy/k8s/statefulset.yaml`

**Interfaces:**
- Consumes: `GET /health` and `GET /ready` from Task 1; the running StatefulSet
  from Task 4.
- Produces: a pod whose readiness gates Service traffic and whose startup is
  protected from the liveness probe.

**Why this task exists:** without probes, Kubernetes considers a pod ready the
moment its container starts, and never checks whether it is still working. The
three probes answer three different questions, and their *interaction* is the
part worth learning.

- [ ] **Step 1: Add the three probes to the container spec**

| Probe | Path | `periodSeconds` | `failureThreshold` | `timeoutSeconds` | Failure means |
|---|---|---|---|---|---|
| `startupProbe` | `/health` | 2 | 30 | 2 | still starting |
| `livenessProbe` | `/health` | 10 | 3 | 2 | restart the container |
| `readinessProbe` | `/ready` | 5 | 2 | 2 | withhold traffic |

All three are `httpGet` with `port: http` — the name you gave the container port
in Task 4, so the number is not repeated.

The `startupProbe`'s numbers give a 60-second window (30 failures × 2 seconds).
**While it is failing, the other two probes do not run at all.**

That suspension is the whole reason it exists. Your engine replays its entire log
before `axum::serve` binds the listener, so startup time grows with the size of
the data. Without a startupProbe, a log large enough that replay exceeds the
liveness threshold produces an unrecoverable loop: the pod is killed mid-replay,
restarts, replays from the beginning, takes just as long, and is killed again.
Every restart makes exactly as little progress as the last. This is a real
failure mode for a log-structured store, and it is invisible until the data grows
past a threshold nobody wrote down.

- [ ] **Step 2: Apply and observe the readiness transition**

```bash
kubectl apply -f deploy/k8s/statefulset.yaml
kubectl get pods -n kvs -w
```

Expected: the pod is replaced, and the `READY` column shows `0/1` before `1/1`.
That gap is the readiness probe: the container is running and the process is
serving, but Kubernetes is withholding traffic until it says it is ready.

- [ ] **Step 3: Watch the Service endpoints follow readiness**

In one terminal:

```bash
kubectl get endpoints kvs -n kvs -w
```

In another, delete the pod to force a restart:

```bash
kubectl delete pod kvs-0 -n kvs
```

Expected: the endpoint list empties when the pod goes away and repopulates only
when the new pod reports ready. This is the mechanism that will keep traffic off
a replica still catching up, once replication exists.

- [ ] **Step 4: Break the startupProbe deliberately**

Temporarily comment out the `startupProbe` block and set the `livenessProbe` to
`initialDelaySeconds: 0`, `periodSeconds: 1`, `failureThreshold: 1`. Apply.

Expected: the pod restarts repeatedly, `RESTARTS` climbing, and
`kubectl describe pod kvs-0 -n kvs` shows `Liveness probe failed` events followed
by `Killing`.

This is what a too-aggressive liveness probe does to a service that needs a
moment to start. Your server actually starts fast enough to survive most of the
time, so you may need `failureThreshold: 1` with `periodSeconds: 1` to reproduce
it reliably — the point is to see the loop, not to measure it.

Then restore both blocks and apply again. Confirm the pod returns to `1/1` and
`RESTARTS` stops climbing.

- [ ] **Step 5: Commit**

```bash
git add deploy/k8s/statefulset.yaml
git commit -m "deploy: add startup, liveness, and readiness probes"
```

## Task 6: The verification experiments

**Files:**
- Create: `deploy/README.md`

**Interfaces:**
- Consumes: everything above.
- Produces: a written checklist someone can follow to confirm the deployment
  behaves as the spec claims.

**Why these stay manual:** the value is in watching the cluster react.
Automating them means writing rollout-waiting and retry logic that teaches
nothing about Kubernetes, and none of these are regressions likely to reappear
silently. The 70-test suite remains the automated safety net.

Write each experiment into `deploy/README.md` as you run it, including what you
actually observed. A checklist that records real output is worth considerably
more later than one that restates the plan.

- [ ] **Step 1: Experiment 1 — data survives pod deletion**

```bash
kubectl port-forward -n kvs svc/kvs 3000:3000 &
curl -X PUT localhost:3000/v1/kv/alpha \
  -H 'content-type: application/json' -d '{"value":"one"}'
curl -X PUT localhost:3000/v1/kv/beta \
  -H 'content-type: application/json' -d '{"value":"two"}'

kubectl delete pod kvs-0 -n kvs
kubectl wait --for=condition=ready pod/kvs-0 -n kvs --timeout=60s
```

The port-forward dies with the pod. Restart it, then:

```bash
curl -i localhost:3000/v1/kv/alpha
curl -i localhost:3000/v1/kv/beta
```

Expected: both keys return 200 with their values. `kubectl logs kvs-0 -n kvs`
shows a fresh startup, and `kubectl get pvc -n kvs` shows the *same*
`data-kvs-0` claim with the same age — the pod was replaced, the storage was not.

This is the PersistentVolumeClaim and your replay path working together.

- [ ] **Step 2: Experiment 2 — no acknowledged write is lost across a rolling update**

Write several keys, then trigger a rollout by changing something in the pod
template. The simplest honest change is an annotation:

```bash
kubectl patch statefulset kvs -n kvs -p \
  '{"spec":{"template":{"metadata":{"annotations":{"rollout":"1"}}}}}'
kubectl rollout status statefulset/kvs -n kvs
```

Then re-establish the port-forward and confirm every key survives.

**What this proves, and what it does not.** With one replica and a
`ReadWriteOnce` volume, a rolling update is necessarily serialized: the old pod
terminates fully before the new one starts, so there is a window with no server.
The property demonstrated is that **no acknowledged write is lost**, not that
there is no downtime. Zero downtime requires replication.

Watch `kubectl logs kvs-0 -n kvs` during the rollout. The old pod's final lines
are your graceful shutdown running inside the termination grace period — SIGTERM,
HTTP drain, channel close, `Engine::sync`, thread join.

- [ ] **Step 3: Experiment 3 — readiness gates traffic**

Already observed in Task 5, Step 3. Record what you saw: the endpoint list
emptying and repopulating, and the `0/1` → `1/1` transition.

- [ ] **Step 4: Experiment 4 — the startupProbe earns its place**

Already run in Task 5, Step 4. Record the restart-loop behaviour and the
`describe` output that identified it.

- [ ] **Step 5 (optional): Experiment 5 — the keydir's memory ceiling**

Lower `resources.limits.memory` to `64Mi`, apply, and write keys in a loop until
the pod is killed:

```bash
for i in $(seq 1 200000); do
  curl -s -o /dev/null -X PUT "localhost:3000/v1/kv/key-$i" \
    -H 'content-type: application/json' -d '{"value":"padding"}'
done
```

Expected: eventually `kubectl get pod kvs-0 -n kvs` shows a restart, and
`kubectl describe pod kvs-0 -n kvs` reports `Reason: OOMKilled` in the last
state.

This makes a design property visible: your keydir holds every key in memory, so
the pod's memory limit is a hard ceiling on how many keys the store can hold, and
crossing it presents as a crash rather than as a capacity error. Compaction will
not help — it reclaims disk, not index memory.

Restore the limit to `512Mi` when you are done.

## Done

The store runs under an orchestrator, its data outlives its pod, and the
shutdown path you wrote in the MVP is exercised by something other than your own
Ctrl-C.

Two follow-on projects, each needing its own spec and plan:

**Compaction** — engine-local, and the natural next piece. Multiple log files, a
merge that rewrites live records into a new generation, and `Entry.file_id`
finally earning the field it has carried since Phase 1.

**Replication** — the large one. This deployment already provides what it needs:
`volumeClaimTemplates` for per-replica storage, headless DNS for peer addressing,
ordered rollout for one-at-a-time updates, and `/ready` as the catch-up gate. The
work that remains is in Rust: a log index on each `Command`, a replay-driven
writer loop, a replication protocol, and a decision about whether a primary is
statically assigned or elected.

Section 7 of the spec records what was deliberately deferred here —
PodDisruptionBudgets, metrics, structured JSON logging, Kustomize overlays,
distroless images, ConfigMaps, and multi-arch builds — and why each is better
motivated after replication exists.
